# 项目经验与防复发约定

这份文档记录《终端三国》开发过程中已经确认的产品方向、工程经验、曾经出现的问题，以及后续修改必须执行的检查。它是维护约定，不是游戏内介绍。

## 一、已经确定的产品约束

- 项目名称是“终端三国”，游戏内品牌显示为“<<<三国”，游戏界面不再出现“终端”字样。
- 游戏内界面使用中文，不混入英文按钮、标题或状态文字。
- 视觉方向是复古电脑系统与终端配色的结合：暗绿、黄褐、高反差边框、实色标题栏，不使用现代渐变标题栏。
- 界面应紧凑，字号和窗口都不能过大；优先通过分组、分页、二级菜单和独立窗口解决信息拥挤。
- 桌面窗口必须共用统一模板：标题、拖动区、最小化、最大化、关闭、缩放柄、激活态、任务栏状态和持久化行为一致。
- 窗口控制按钮位于标题栏最右侧。标题栏交互、任务栏按钮、府库托盘和历法托盘都必须保持一致的最小化切换语义。
- 窗口吸附距离固定为 5 像素。任务栏左右贴紧屏幕，不留空档。
- “漢”是左下角正方形系统按钮；功能较多时使用二级菜单，不把所有入口堆在一级菜单。
- 所有普通界面文字默认不可选择，输入框和可编辑区域例外。
- 刷新浏览器只允许重建界面，不能退出当前战局、短暂闪回主菜单或打乱窗口版面。
- 版面预设允许保存多个槽位，并包含普通窗口和情报、外交、人物等资料弹窗的位置、大小、最小化与最大化状态。
- 观察模式外交图不强行设置中心势力；玩家模式才以玩家势力为中心。
- 事件、报告和资料面板都应表现为同一套可管理窗口，不再混用传统网页弹窗。

## 二、有效的工程经验

### 1. 先明确用户描述的是哪一层

相似说法可能对应完全不同的功能：

- “按钮的 hover 反馈”是按钮自身的颜色、边框、亮度和按下状态。
- “悬浮提示”是鼠标停留后出现的说明框。
- “按钮被盖住”可能是按钮本身、菜单、子菜单或说明框的层级问题。

修改前必须先用浏览器复现，并检查目标元素的实际计算样式、事件和层级，不能仅凭上下文猜测。

### 2. 共同行为必须在公共层解决

所有按钮都需要视觉反馈，就应提供全局的 `hover`、`active`、`focus-visible` 和 `disabled` 规则，再允许具体组件补充样式。所有窗口都需要标准控制，就应由窗口管理器统一创建和管理，不能在每个弹窗里重复拼装。

局部补丁只能用于真正的局部差异。若用户使用“所有”“统一”“标准化”等词，验收范围必须覆盖全局。

### 3. 游戏状态与桌面状态分层持久化

战局数据、当前会话标记、普通窗口版面、动态弹窗版面和用户预设是不同层次的数据。刷新恢复顺序应为：

1. 在首帧前识别活动战局，阻止主菜单闪现。
2. 恢复战局状态。
3. 创建桌面窗口和动态弹窗。
4. 恢复窗口位置、尺寸和形态。
5. 最后执行视口约束，避免窗口落在屏幕外。

默认布局只能用于没有几何记录的窗口，绝不能覆盖已经保存的用户位置。

### 4. 视觉层级要按浏览器机制设计

单纯增加 `z-index` 不能解决所有遮挡。原生 `dialog`、`popover` 会进入浏览器顶层，普通定位元素即使拥有很大的 `z-index` 仍可能在其下方。系统菜单和需要越过窗口显示的说明框应使用合适的顶层机制，并验证打开、关闭及焦点行为。

### 5. 动态生成的界面也属于验收范围

运行后才生成的任务栏按钮、菜单、图例、资料窗口和事件窗口，必须与静态 HTML 中的控件使用相同的组件规则。测试不能只扫描初始页面源码，还要在真实战局中打开这些界面进行检查。

### 6. 静态资源修改必须更新缓存版本

修改 CSS 或 JavaScript 后，应同步更新 `index.html` 中对应资源的查询版本。否则浏览器可能继续使用旧文件，表现为“代码已经改了但界面没有变化”。版本更新本身也应被测试覆盖。

### 7. 自动测试与真实浏览器检查缺一不可

源码测试适合检查结构、关键规则和防止回归，但不能证明视觉效果真实存在。涉及布局、hover、拖动、遮挡、刷新和响应式适配时，必须补充真实浏览器验证。

## 三、这次及此前出现过的错误

### 1. 把 hover 视觉反馈误解成悬浮说明

这次一开始只检查了 `data-tip`，遗漏了按钮本身的视觉变化；随后又把“浮现提示”误作虚线描边，方向反复。正确实现是：全部按钮的悬浮变色、键盘聚焦与禁用反馈统一放在 `css/button-states.css`；鼠标悬浮不加描边，按压状态仍由原组件负责；所有静态及动态按钮由 `app.js` 统一补充简短浮现提示。

### 2. 只修复“漢”菜单，没有验证全局按钮

此前修复集中在系统菜单，测试也只验证菜单按钮拥有说明数据，无法发现任务栏、页签和普通按钮仍无明显 hover。以后凡是全局交互要求，统一状态只允许在 `css/button-states.css` 维护，并至少抽查主菜单、任务栏、窗口控制、页签、表单按钮、图例和动态弹窗七类控件。

### 3. 用层级数值处理浏览器顶层问题

曾经出现系统菜单或条目说明被窗口遮挡。只调高 `z-index` 不可靠，后来改为顶层显示机制。以后先判断元素是否处于 top layer，再决定使用 `z-index`、`dialog` 还是 `popover`。

### 4. 窗口能力逐个追加，导致行为不一致

最小化、最大化、关闭和标题栏结构曾在不同窗口间不一致，并出现双标题。根因是功能先按窗口追加，标准模板形成得太晚。以后新增窗口必须先接入窗口管理器，不允许自行复制控制按钮。

### 5. 只保存战局，没有完整保存界面会话

刷新曾返回主菜单、先闪主菜单再恢复、窗口位置被默认布局覆盖。根因是战局恢复、首帧显示和桌面布局恢复没有形成完整时序。以后改动启动与存档逻辑时，必须执行刷新连续性检查。

### 6. 弹窗尺寸和定位影响了页面滚动

新弹窗曾把页面顶起或让整个页面上移。以后所有桌面弹窗都应固定在视口内，由弹窗内容区自行滚动，并测试最大化、小窗口和窄屏三种情况。

### 7. 信息架构靠堆叠而不是分组

图例与旬报合并后文字过密，“漢”菜单功能增加后也过于拥挤。后续通过天下大势与旬报分页、二级菜单解决；图例一度独立成窗，但舆图本身已用页签高亮表达图层，独立图例窗既重复标题又占版面，最终并回舆图窗口底部。以后增加入口前先判断它属于现有分组、二级菜单还是独立窗口；已在主体窗口内的内容不要再单独开窗。

### 8. 测试名称与实际断言不一致

原测试把“拥有 `data-tip`”称为“悬停反馈”，掩盖了视觉状态缺失。测试名称必须精确描述断言对象，不能把提示内容、视觉状态和交互结果混为一谈。

### 9. 多份存档副本按“存在”取用，而不是按“新旧”取用

同一战局同时存在浏览器副本、本地游戏服务存档与自动备份。载入侧原先只要浏览器副本存在就直接返回，本地服务里更新的战局只有回填浏览器副本成功才会生效。浏览器配额写满后回填失败，刷新就恢复成旧战局，表现为“刚占领的城池全没了”。任何多副本数据都必须显式比较时间戳取最新，并记录实际采用的来源；只靠“某一份存在”决定优先级，等于把最新进度交给最容易写满的那一份。

### 10. 舆图几何只保留一份实现

地形、州域、郡域、水路、地标与道路此前只存在于 `js/ui/map-view.js` 的绘制代码里，任何工具想读写同一张舆图都只能复制这些公式，改动一处就会与画面悄悄分叉。抽出的 `js/core/map-grid.js` 把网格生成、RLE 分层编解码、路网与校验收敛为唯一实现，`MapView` 只做绘制、`MapEditor` 只做编辑；两者都调用 `MapGrid`，所以编辑器里的改动与画面里的格子必然一致。凡是「画面上看到的东西也要能被编辑/导出」的数据，都必须先有脱离表现层的纯数据定义。

### 11. 界面入口前置时，弹窗不能绑死在开局之后的实例上

舆图编辑器原先只服务进行中的战局，`install({state,mapView})` 在开局完成后才执行，把数据源、地图视图和弹窗一次性绑死。入口移到开始界面后，弹窗要在「游戏尚未创建」时就能打开，且要跟随用户新选的剧本切换数据。改成 `install({getData,getMapView})` 取值函数后，同一个弹窗在开始界面读所选剧本、入局后读 `state.data`，`mapView` 为空时只提示「写入剧本数据」，不再假定视图一定存在。凡是入口可能出现在生命周期不同阶段的弹窗，数据来源都应以取值函数传入，而不是在安装时固定引用。

### 12. 叠加层与读数条：别让网格自动排布把提示挤到错误的位置

给编辑器加悬停指示框时，最小改动看似是把叠加 `<canvas>` 和读数 `<p>` 直接塞进原来的网格容器，但 `grid-auto-flow:row` 会按 DOM 顺序把新节点补到右边一列，读数条会被挤到侧栏上方、侧栏掉到第二行。正确的做法是把「棋盘 + 读数条」包成一个 `.map-editor-column` 子网格，让容器仍然只有两块；叠加层则放进 `.map-editor-canvas-wrap`（`position:relative`）并让位图在每次 `drawCanvas()` 里与主画布同尺寸，才能保证像素对齐；`pointer-events:none` 保证它不吃掉光标与画笔事件。新增节点前先确认父容器的排布方式，比事后调试位置更省事。

### 13. 下拉候选要覆盖“数据里已经存在的值”，而不是只列定义表

舆图编辑器的笔刷取值当初直接取 `terrainDefs` 的键，看起来够用：地形定义表就是全部合法取值。但分层里可能已经出现未登记的值（导入补丁、旧存档），州域/郡域更是只有分层与剧本数据才知道有哪些名字——`辽东`、登记表里的 `琅邪国` 都不会出现在任何「定义表」中，于是用户明明地图上有这个值却选不到。候选集合应当是「定义表 ∪ 分层现存 ∪ 剧本数据声明」，界面上用一个下拉就把全部取值列出并给出可读标签（`平原（plains）`），默认选中该层出现次数最多的取值，并记住每层上次的选择。凡是「让用户从既有取值里挑一个」的场景，就只要一个从实际数据汇总的下拉；把一个下拉加一个手填框并排摆出来，只会让用户分不清该动哪个。

### 14. 编辑器要按“工具”分派画布操作，不能所有点击都落到同一个图层笔刷

舆图编辑器最初只有一个隐式的图层笔刷：画布上按下、拖拽一律写当前图层。侧栏虽然并排摆着「图层笔刷」「据点」「道路」三块面板，但它们只是控件集合，Canvas 的指针事件根本不看用户正在改什么——于是用户切去修道路，点地图还是改地形。正确做法是显式引入工具状态（`activeTool`），由画布指针事件统一调用 `applyTool(x,y)` 再按工具分派到绘制图层、选中/移动据点、拾取道路起终点，并且只显示当前工具的面板、只高亮当前工具的按钮。凡是「同一个画布/画布区域承载多种编辑语义」的界面，都要有一个显式的工具切换，而不是靠面板可见性暗示。

### 15. 自绘下拉在选项被程序改写后必须重建

自绘下拉 `TerminalSelect` 会隐藏原生 `<select>` 并另建一份按钮列表，而这份列表只在「下拉自身触发 `change`」时重建。编辑器里的 `#mapEditorValue` 在 HTML 中是一个空 `<select>`，打开编辑器时由脚本用 `innerHTML` 写入取值——程序改写选项既不会触发 `change`，也不在任何观察范围内，于是界面上的下拉始终是「请选择」，表现为「笔刷值啥都没有」，而数据层测试却全绿（桩 DOM 直接读 `select.options`，绕开了自绘层）。修法是两层都补：`TerminalSelect` 侧在新增节点属于已增强 `select` 时重建控件，使用侧在写完选项后显式 `refresh`。教训是「测试读到的是原生控件，用户看到的是代理控件」时，任何以原生控件为断言的测试都不能证明界面正确；代理层的同步必须由代理层自己保证，并且要有针对代理层的回归测试。

### 16. 地图元素要按当前上下文显示，并且开关要按工具记忆

舆图编辑器的画布长期无条件叠加网格、道路和据点，于是三个工具看上去一模一样：用户在画笔上改地形时被道路和据点标签干扰，想要「不要全部都显示」却没有任何开关。修法是两层——按工具给出默认显示集合（图层笔刷看地形与水道地标、据点看据点与县治、道路看据点与道路），再用一组勾选框让用户手动固定。关键在于开关的存法：如果只存一份全局开关，用户切一次工具就要重新勾一遍；如果做成「自动 / 手动」双态，又得额外解释怎么回到自动。这里把状态按工具分开存（`elementState[tool][key]`），切工具即恢复该工具自己的设置，「手动」就是它本身的记忆，没有第二套语义。另一个容易漏的点是交互反馈：道路工具的起终点虚线是正在进行的操作，不能因为用户隐藏了道路图层就一起消失。凡是「同一画布按模式显示不同元素」的界面，都要区分「数据元素」与「操作反馈」，前者可开关，后者不随开关隐藏。

### 17. 保存要覆盖完整生命周期，读档也要刷新所有显示缓存

编辑器在开始界面「应用」曾只改内存，刷新和重新选择剧本就丢失；战局读档虽然还原了水道数据，`MapView` 却保留上一局的水道和地标数组。数据恢复与画面恢复是两个独立环节，必须都验证。剧本持久版本、未应用草稿、战局存档分开保存，写入成功后才应用；原始剧本保留独立基线，避免自定义地图污染旧存档。验证必须走真实的保存按钮、刷新、新开局和同页换档，并模拟写入、删除失败。入口前置到开始界面后，提示计时器等共享依赖也要在等待开局前初始化，不能只移动按钮却留下开局后的未初始化变量。

### 18. 扩展行政节点时要同步人口来源，不能用“条目存在”代替有效数据

新增郡治曾写入 `[郡名,140,null,区域]`，同时保留已复用节点的废弃人口条目，导致表长度看似足够但实际口数缺失；县表又使用勃海、京兆尹及三辅，查不到同一统计口径。人口来源应先按105个郡国集中登记，再派生实际城市ID的资源配置，校验每个节点而不是只比较总条数。户数不是口数，三辅合计不是京兆尹，前期统计、校勘值、游戏估值都不能冒充140年实测人口。生成脚本必须复用相同来源并自动同步，离线镜像也要实际生成县人口。更新历史来源时保留旧战局当前人口，自定义疆域不得继续展示原郡的统计数。

## 四、每次界面修改的最低检查清单

地图编辑器补充约定：宽窄窗口都检查左右栏和固定提示条的实际边界，不能只验收画布一侧；编辑视口与工具栏、状态栏分别布局，避免用多个 `vh` 上限相互补丁。连续绘制以完整手势作为撤销单位；导入必须先校验副本，完整回读道路、县治和空覆盖层。应用之后必须实测存档刷新，不能把内存里的应用成功当作持久化成功。草稿保存不能依赖已经接近配额上限的战局 localStorage，详见 [舆图编辑器](MAP_EDITOR.md)。

- 在已打开的真实存档中测试，不只看主菜单或空白状态。
- 刷新后仍在同一战局，没有主菜单闪现，窗口位置与形态不变。
- 鼠标移入、按下、键盘聚焦、禁用四种按钮状态可区分。
- 新窗口具备统一的最小化、最大化、关闭、拖动、缩放和任务栏行为。
- 打开多个窗口、菜单、子菜单和说明框，检查顶层遮挡。
- 检查 5 像素吸附、屏幕边界约束和任务栏全宽。
- 检查默认桌面、玩家模式、观察模式和窄屏布局。
- 检查中文文案、游戏内品牌、重复标题和无用介绍文字。
- 修改静态资源后更新缓存版本。
- 涉及存档的改动要在“浏览器副本 = 服务端存档 = 备份”之间确认按时间取最新，并实测刷新后续玩不倒退。
- 运行全部自动测试；按钮反馈可运行 `node tools/qa-hover-feedback.mjs`，再用真实浏览器走一遍受影响路径。

## 五、后续修改原则
